# Privacy and Data Handling

## Scope

The included benchmarks and explicit demo are simulations. Model training on
those data does not authorize processing a bank's customer data. Do not enter
real identifiers in the local demo, screenshots, CI fixtures or public reports.
The service is not approved for production decisions or regulatory submission.

Account, transaction, originator device and IP identifiers are tokenized at the
authenticated backend boundary using independent tenant/domain HMAC namespaces.
This is pseudonymization, not anonymization: relationships, amounts and timing
can still enable linkage. The ML service receives tokens, not the original vault
payload or encryption key. Tokens must not be treated as public customer data.

Original inputs and free-text review rationales are encrypted with AES-GCM;
tenant identity is authenticated associated data. Nonces are generated per write.
The encrypted vault is separate from the tokenized ledger. The runtime DB role
cannot edit accepted ledger entries, policy history or audit entries and cannot
read the retired legacy application tables. Existing legacy storage is preserved
for controlled migration, not silently deleted or made available through new APIs.

## Access and Retention

OIDC tenant and role claims are required; the identity provider must make tenant
assignment administrator-controlled. Analysts cannot change policy or approve
holds, auditors cannot mutate cases, and streams cannot cross tenant namespaces.
Local password authentication exists only in the explicit demo profile, with
separate per-install passwords. No credential is a customer authorization grant.

Before any non-simulated deployment, the data controller must approve and enforce
purpose, lawful access, retention, deletion, appeal and incident procedures for
each store: vault, tokenized ledger, decisions, feedback, audit, Redis and backups.
Redis snapshot expiry is only cache eviction, not customer erasure. Hash chaining
does not exempt an audit record from privacy requirements. Do not put plaintext
PII in audit metadata; free text is encrypted but still requires retention review.
Automatic full data-principal erasure and legal-hold workflows are not implemented.

Public reports must contain only authorized benchmark evidence. Per-tenant audit
exports and STR drafts are restricted data, not README assets. Backups and
database volumes need deployment-level encryption, access controls and tested
restore/deletion procedures; application column encryption is not full-disk TLS
or backup protection. Secret files inside a cloud-synced working directory may
also be synced: production secrets belong in a managed secret store, not OneDrive.

Original identifier recovery is not exposed as a public API. Authorized security
operators can correlate actor pseudonyms with approved identity-provider records.
Keep that mapping access separate from general model/feature access. Encryption
master-key rotation requires an authenticated re-encryption/key-version migration;
changing an environment value alone does not rotate existing ciphertext safely.

## India Review

Deployment review must consider notices, lawful processing, data-principal rights,
security safeguards, breach response, processors, transfers, retention and any
applicable financial-record obligations. Do not infer which provisions are in
force solely from an Act's title: commencement is phased in official notifications.
Use the [India Code Act text](https://www.indiacode.nic.in/bitstream/123456789/22037/1/a2023-22.pdf),
[commencement notification](https://upload.indiacode.nic.in/showfile?actid=AC_CEN_45_0_00003_2023-22_1763464807080&filename=c56ceae6c383460ca69577428d36828b.pdf&type=hindinotification)
and [MeitY rules and corrigendum index](https://www.meity.gov.in/documents/act-and-policies/digital-personal-data-protection-rules-2025-gDOxUjMtQWa).
These are engineering notes, not a legal opinion or compliance certification.
